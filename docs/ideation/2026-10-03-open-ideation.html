The pattern

The six idea agents worked independently and kept arriving at the same place: what happens after a red run. The tool can build and run a scenario across HTTP, web and Android. When a run fails, it gives you an error string and a folder path. It already records every retry attempt in SQLite, and nothing reads those rows back.

The survivors fall into two tracks. Trust in green (ideas 1, 2 and 6) is about whether the integration check in the consumer project can be believed. Why did it fail (ideas 4 and 5) is about cross-channel diagnosis. Idea 3 stands alone and is time-sensitive, because it revisits a storage decision made this week.

Grounding Context

Codebase Context

  • CLI commands run, check, list, export, init, ui (src/cli.ts:63). Drivers: http, web (Playwright), mobile, adb-flow, shell.
  • The last ~60 commits were consolidation: UI split into view folders, backend split into per-concept modules, browser smoke tests, DB-first scenario storage (commit 4fdf4ac). docs/backlog.md says "Nothing open."
  • Failure evidence varies by driver. Web keeps a full Playwright trace on failure (src/drivers/web.ts:37, :405). Mobile keeps one screenshot (src/drivers/mobile.ts:159-165). HTTP keeps nothing (src/drivers/http.ts:91).
  • step_runs stores one row per attempt, with attempt, iteration, duration_ms and result_data, plus an index on step_id. Run status is only RUNNING, PASSED, FAILED or CANCELLED.
  • Preflight health probes exist (src/preflight.ts:37-44) and run only before a run.
  • There is no CI in this repo, only a pre-push hook. The one real consumer project uses this tool's suite as its integration check.

External Context

  • Playwright Trace Viewer is the benchmark for failure diagnosis, but only for one channel. No tool found offers it for a mixed API, web and Android run.
  • Hurl, Bruno, Karate and Step CI chain captured values between requests, but each covers only one channel.
  • Playwright Test Agents (v1.56+) ship a healer that repairs failing locators. Write-ups warn that healing and retries can hide real bugs.
  • Useful analogies: Temporal durable execution (replay, resume from a step) and the chaos-engineering steady-state check (probe the environment to tell an environment failure from a test failure).

1. Label every failure: environment, product, or test

Idea 1Confidence 80%Complexity Low–MediumTrack: trust in green
Description
When a step fails, re-run the preflight health probes for the services that step touched, and run adb get-state for the device. Record a failure label on the step run. ENV means a service or device is down. PRODUCT means the environment is healthy and an assertion failed. TEST means the environment is healthy and a locator or timeout failed. Show the label in the runner's failing-steps view, in the CLI summary and in summary.json. Optionally stop running further scenarios against a service that is down, so one crash does not turn into twenty red scenarios.
Basis
  • direct: src/preflight.ts:39 fetch(new URL(service.health ?? "/", service.url), { signal: AbortSignal.timeout(3000) }) is called only before the run.
  • direct: docs/domain/runs.md status is only "RUNNING", "PASSED", "FAILED", "CANCELLED".
  • external: the chaos-engineering steady-state hypothesis (principlesofchaos.org).
  • All six agents proposed this independently.
Rationale
A run that depends on a backend, a dev server and an emulator turns red for infrastructure reasons often. Today each red run starts with someone ruling out "the server died" by hand. The consumer uses this suite as its integration check, so a label that separates infrastructure from product is what keeps people reading red results instead of ignoring them.
Downsides
A probe taken after the failure can race a service that has already recovered, so the label is a strong hint, not proof. The label adds a dimension to run status, so docs/domain/runs.md must change in the same commit. The ENV/PRODUCT/TEST taxonomy needs a short design discussion.

80%
Complexity
Low–Medium

2. Flake ledger: stop counting "passed on retry" as plain green

Idea 2Confidence 80%Complexity LowTrack: trust in green
Description
Read back the attempt rows the runner already writes. Show a step that passed only on attempt 2 or later as recovered: yellow, counted in the run summary ("2 steps passed only after retry"), and optionally treated as a failure under --strict. Add a per-step history view with pass rate, retry-rescued rate and p95 duration across runs and repeat iterations. Later, suggest a retry.times value or a quarantine flag based on that history.
Basis
  • direct: src/runner.ts:331 const attempts = (raw.retry?.times ?? 0) + 1, and each attempt gets its own row id that includes the attempt number (src/runner.ts:338).
  • direct: src/db/connection.ts attempt INTEGER DEFAULT 1, iteration INTEGER DEFAULT 1, and idx_step_runs_step.
  • A grep for flaky or recovered across src, ui/src and docs finds nothing.
  • external: write-ups on Playwright's healer, mabl and Testim warn that automatic recovery hides real bugs. A retry is the low-tech version of the same thing.
Rationale
The data is collected and indexed, and nothing reads it back. Retries quietly turn a regression into a slow pass, and Android steps are the most likely to be retried. This is the cheapest idea here that changes what a green result means.
Downsides
Deciding whether "recovered" fails the run is a policy question. A per-step history needs stable step identity across edits, which idea 5 provides. The duration-trend part (control charts) only pays off once there are enough runs.
Confidence
80%
Complexity
Low

3. Keep scenarios reviewable in git

Idea 3Confidence 75%Complexity Low (check) / Medium (write-through)Time-sensitive
Description
Since commit 4fdf4ac, GUI saves and deletes change SQLite only, and SQLite lives in the gitignored .e2e folder. A scenario edited in the GUI is invisible to code review until someone remembers to export. Two options:
  • (a) Drift guard. Keep DB-first and add e2e export --check, which fails when the DB and the JSON files disagree. Run it from the consumer's pre-push hook.
  • (b) Write-through. Every save writes a deterministic, sorted-key JSON file, and every delete removes it. On load, re-import any file whose content hash changed, replacing the one-time import flag.
Basis
  • direct: docs/domain/scenarios.md section 4 says POST and DELETE on /api/scenarios "change SQLite only and never touch JSON files". Import runs once, after which scenarios_imported_at is set and it "never imports again". Export "leaves files for deleted ids in place".
  • direct: .gitignore lists .e2e, and src/db/paths.ts sets DEFAULT_DB_DIR = ".e2e".
Rationale
For the consumer, scenario diffs in a PR are how a team reviews its integration check. If the export is forgotten, the suite in git is not the suite that runs. The decision is days old, so changing it now is cheap. Once habits and more consumers depend on it, it is not.
Downsides
It re-opens a decision that was just made. Write-through brings back the "deleted scenario comes back from a leftover file" problem that DB-first solved, unless deletes are handled carefully. Option (a) is cheap but only detects drift and does not prevent it.
Confidence
75%
Complexity
Low for (a), Medium for (b)

4. One cross-channel failure timeline

Idea 4Confidence 70%Complexity HighTrack: why did it fail
Description
For a failed scenario, place every step on one time-ordered view in ArtifactsView: the HTTP request and response, the web trace, Android evidence, the variables before and after each step, and lines from the services that preflight started. The goal is a Trace Viewer for a mixed run, where you can see what the API returned two steps before the Android screen went wrong.
  • First slice (small, standalone): bring Android evidence up to web's level. On failure, save adb logcat -d (cleared at scenario start), a uiautomator dump and, optionally, a short screenrecord.
  • Second slice: save HTTP request and response pairs per step, and save resultData on failed step runs, which is not saved today.
  • Third slice: the unified view.
Basis
  • direct: src/drivers/web.ts:405 tracing.stop(failed ? { path: join(artifactsDir, "web-trace.zip") } : undefined). Web is already covered.
  • direct: the mobile driver writes only mobile-failure.png (src/drivers/mobile.ts:159-165), and logcat does not appear anywhere in src.
  • direct: src/drivers/http.ts:91 endScenario keeps no evidence.
  • external: Playwright Trace Viewer is the single-channel benchmark, and no cross-channel equivalent was found.
  • Seven of the seven idea reports proposed a form of this.
Rationale
Mixing channels in one scenario is the only thing Hurl, Bruno, Maestro and Playwright cannot do. The tool's failure experience is still one channel at a time, so it gives up its advantage at the moment it matters most. The first slice is cheap and fixes the worst gap: Android is the slowest channel and has the least evidence.
Downsides
Large overall. Disk use grows, so a retention policy is needed. The unified view is a substantial UI piece. Correlating backend service logs depends on each service's log format.
Confidence
70%
Complexity
High overall; the Android slice is Low

5. Pin each run to the exact scenario it ran

Idea 5Confidence 75%Complexity LowTrack: why did it fail
Description
Store a content hash of the scenario on each run, and the substituted step JSON on each step run. The runner already computes that JSON. Run history then describes what actually ran, and "what changed between the last green run and this red one" becomes a query: the scenario, the product, or both.
Basis
  • direct: the runs schema in docs/domain/runs.md has no scenario version or hash column.
  • direct: step_runs.step_id is documented as a reference to scenario_steps(id) "if known", and auto-save edits that row in place.
  • direct: src/runner.ts computes const step = substitute(raw, scope) and stores only status, code and message.
Rationale
Moving scenarios to SQLite removed git as the version history. History is already shown in the GUI and can mislead after an edit. This is cheap now and costly to backfill later, and ideas 2, 4 and 7 all build on it.
Downsides
It is a schema change with a domain-doc update. Storing step JSON per attempt grows the database, so it may need pruning alongside run retention.
Confidence
75%
Complexity
Low

6. CI-readable run output for the consumer

Idea 6Confidence 65%Complexity Low–MediumTrack: trust in green
Description
Add e2e run --ci (or --reporter junit). It writes JUnit XML and a GitHub step summary, zips artifacts for each failed scenario so they can be uploaded, and uses exit codes that separate an environment failure (idea 1) from a product failure. This is an output format, not a deploy workflow for this repo.
Basis
  • direct: the runner writes only a custom summary.json (src/runner.ts:260), and a grep for junit finds nothing.
  • direct: the grounding says there is no CI pipeline in this repo, and that the consumer runs this suite as its integration check.
Rationale
An integration check that only runs when a person starts it locally gets skipped. Standard reports let the consumer gate merges on the suite. The JUnit attempt and flaky fields also carry idea 2's data into CI dashboards.
Downsides
This repo has no CI of its own to test it in. The value depends on the consumer adopting CI, which is outside this repo's control.
Confidence
65%
Complexity
Low–Medium

7. Re-run from the failed step

Idea 7Confidence 50%Complexity Medium–HighTrack: authoring speed
Description
Save the extracted-variable scope after each passing step. e2e run --resume <runId> and a "Re-run from here" button restore that scope and start at the failed step, instead of replaying login, seeding and slow Android navigation. Resumed runs are labelled partial and never count as green. A scenario can opt out with resumable: false.
Basis
  • direct: src/runner.ts extract(step, result, scope.ctx) is the only state passed between steps, so the state to save is well defined.
  • direct: step_runs.result_data is stored for passed attempts (src/runner.ts:374), which are the rows a resume needs.
  • external: Temporal durable execution (event history, replay, resume).
  • All seven idea reports proposed this.
Rationale
Fixing a locator at step 14 of an Android and API scenario means replaying steps 1 to 13 for every attempt. That loop is where authoring time goes. The verifier rated this weak, and I kept it anyway: every frame converged on it, and its concern about missing result_data does not apply, because only passed rows are needed. Its concern about side effects stands, which is why confidence is lower.
Downsides
Real systems drift between the original run and the resume. Data seeded at step 3 may be gone, especially if teardown is added later. The Temporal analogy covers replaying deterministic code, not live side effects. It needs clear rules on when a resume is valid, plus a domain-doc change.
Confidence
50%
Complexity
Medium–High

Grounding Context

Codebase Context

  • Scenarios live only in SQLite (scenarios, scenario_steps with an actions JSON column, step_presets, step_groups). JSON files are written by e2e export and read back only by an explicit e2e import (docs/domain/scenarios.md:133-138).
  • An agent today has two ways in: POST /api/scenarios, or a hand-written JSON file plus e2e import. No MCP server, no agent-facing docs, and AGENTS.md holds only rules for developing this repo.
  • POST /api/scenarios saves the scenario before it reports validity: it calls saveScenario, then returns { ok: true, isValid, errors } (src/server/routes/scenarios.ts:57-63). An agent that reads ok: true has stored an invalid scenario.
  • Validation has two layers that disagree. checkSteps rejects run, flow and params (src/scenario.ts:24-28), while schema/v1/scenario.schema.json:92-99 still declares them valid. Unknown actions fail only at run time (src/drivers/web.ts:387). Errors are plain strings; there is no --json output.
  • The action vocabulary lives in per-driver switch statements with aliases (tap, tapon, click are one action, src/drivers/mobile.ts:81-83) and in prose in docs/domain/scenarios.md. Valid target and fixture names come from the project config, so no static doc can list them.
  • The runner already captures what an agent would need to see the app, but only on failure: mobile-ui.xml (uiautomator dump), mobile-logcat.txt, http-exchanges.json, and a Playwright trace that is thrown away when a scenario passes (src/drivers/web.ts:402).
  • Each failed step attempt is labeled Environment down, Assertion failed or Step error (src/assertions.ts). --strict fails a run that passed only on retries; --repeat exists. A run with a scenario fixed during Pause on Failure ends FAILED, "so a green run always means nobody stepped in" (docs/domain/runs.md:224).
  • Scenarios have no source, author or review-status column. Scenario versions are fingerprints of what runs, with name, description and ids left out (src/scenario-version.ts).
  • The environment comes from E2E_ENV when set (src/config.ts:159), which any agent shell can set. The consumer app (zomilabu) dev build reports to production Firebase, so the project rule is never to test against production.
  • Real usage is low so far (as of 2026-10-03), so ideas that need lots of run history start with little data.

External Context

  • Playwright Test Agents (v1.56 and later): a planner explores the live app and writes a plan, a generator writes the tests, and a healer replays failures and patches locators. The healer marks a test test.fixme when it judges the product broken. npx playwright init-agents --loop=claude|codex|vscode|opencode writes agent definitions into the repo.
  • Maestro MCP: the agent reads the live view hierarchy and screenshots, writes flow YAML, runs it on an emulator and fixes it until it passes. No AI runs at test time.
  • The tools that work have settled on one pattern: AI writes the test, the test runs deterministically, and AI comes back only to repair a failure. Tools that call a model at run time (Midscene, appium-mcp) cost more per run and give less repeatable results.
  • QA Wolf has a person review every AI-written test before it ships. Most products in this space are cloud services or tied to one framework. A local, web-plus-mobile orchestrator with a run UI over agent-written scenarios has little direct competition.

Topic Axes

  1. Authoring vocabulary: what an agent must know to write a valid scenario
  2. Write path: how an agent's scenario lands in the project
  3. Validate and self-correct loop: the feedback an agent gets before and after a run
  4. Seeing the real app: live ground truth for selectors, texts and API shapes
  5. Human review and run: how the person checks and runs agent output in the UI

Ranked Ideas

  • 1. Agent kit generated from one action registry
  • 2. A strict door for agents, with errors that carry the fix
  • 3. Agent scenarios arrive as drafts with a plain-language readback
  • 4. Probe the dev app by target name
  • 5. The tool checks the agent's "done"
  • 6. Repair packet with label-gated healing
How they fit

Ideas 1, 2 and 3 together are the smallest version of the requested flow. The agent reads the kit, checks its scenario through the strict door until it is clean, and saves it as a draft. The person opens the draft in the UI and approves and runs it. Ideas 4 to 6 raise the share of agent scenarios that pass on the first run, and handle the ones that don't.

1

Agent kit generated from one action registry

Authoring vocabularyConfidence 85%Complexity Medium
Description
Define the action vocabulary once, as data: per driver, its actions and aliases, required and allowed fields, assertion operators, placeholder namespaces (${ctx.*}, ${env.*}, ${run.*}) and removed fields. Generate the JSON Schema, the checkSteps allow-lists, the drivers' unknown-action check and the docs from it. Then serve a project-specific copy, as GET /api/vocab and a generated section for the consumer repo's AGENTS.md (or a skill file). It lists that project's real target names, fixture names and env variable names as enums, its presets and step groups, two or three example scenarios, the invariants (targets by name, no production), and how to validate and save. Aliases keep working at run time but are flagged as non-canonical.
Basis
  • direct: the schema and the checker already disagree. src/scenario.ts:24-28 rejects run/flow/params, and schema/v1/scenario.schema.json:92-99 still allows them. An agent that reads the schema is told invalid fields are valid.
  • direct: src/drivers/web.ts:387 throws "unknown web action" only at run time; src/drivers/mobile.ts:81-83 accepts three spellings of one action.
  • direct: valid targets and fixtures come from the project config (src/scenario.ts:46-49), so they cannot be in generic docs.
  • external: playwright init-agents writes agent definitions into the user's repo. ASD-STE100 uses one approved word per meaning for readers who act on text against real hardware.
Rationale
Every later step depends on this: an agent can't validate, heal or be reviewed well if it starts from a vocabulary that is spread over four places and already contradicts itself. Project-specific enums turn the most likely agent mistake, an invented target name or a raw URL, into an editor-time error in any tool that reads JSON Schema.
Downsides
Refactors validation across src/scenario.ts, src/schema.ts, the schema file and three drivers. Removing run/flow/params from the schema is a tightening, so the schema versioning rule (schema/README.md) may call for a v2. Whether agents get the kit as a file, an endpoint or an MCP tool is still open.
2

A strict door for agents, with errors that carry the fix

Write pathConfidence 85%Complexity Low-Medium
Description
Add POST /api/scenarios/validate, which writes nothing. It runs the schema, checkSteps, target and fixture lookup against the live config, and a check that each ${ctx.*} is extracted before it is used. Agent writes use a strict mode that refuses anything invalid, while the builder keeps its lenient 600 ms auto-save for half-typed steps. Errors come back as objects: { code, path: "/steps/3/actions/0/action", value, allowed, hint, fix }. fix is a JSON Patch when the repair is known: replace a removed field with actions, use the nearest real action for an alias that doesn't exist, use the nearest configured target for an unknown one. The UI and, later, e2e check --json show the same objects.
Basis
  • direct: src/server/routes/scenarios.ts:57-63 calls saveScenario, then returns ok: true, isValid, errors. Invalid agent output is stored today.
  • direct: errors are strings built as steps[${index}] "${step.name}" (src/scenario.ts:52-66), and loadScenarios throws one "Invalid scenarios" blob (src/scenario.ts:131-152). REMOVED_FIELDS already stores the remedy text.
  • direct: the CLI import already refuses invalid files (src/cli.ts:153), and the hold route already validates a single step (src/server/routes/hold.ts). The strict path exists for files and for retries, not for HTTP saves.
  • external: compiler fix-it suggestions (clang, rustc help:); Maestro MCP's write, run, fix loop.
Rationale
Checking its own work is where an agent spends its retries. Without writing anything, it can check a candidate twenty times and leave no rows behind. With a patch attached, most fixes take no extra round trip. The same diagnostics let the builder highlight the bad step for a person.
Downsides
Two save behaviors (lenient for the builder, strict for agents) need a clear rule for which caller gets which. Fix suggestions need a curated list of error codes, which grows over time.
3

Agent scenarios arrive as drafts with a plain-language readback

Human review and runConfidence 70%Complexity Medium
Description
A scenario an agent writes is saved as a Draft, with its source (agent name) and the prompt that produced it. The UI shows drafts in their own group, each with a review card. The card shows the original prompt next to a readback the code builds from the steps, not the agent's own summary ("Open the app fresh on Pixel. Tap 'Sign in'. Type the test email into 'Email'. Check that 'Welcome' appears."). It also lists the targets and fixtures the draft touches. One button, Approve and Run, runs it headed with Pause on Failure. An agent's revision of an approved scenario lands as a draft next to the live one, so a bad rewrite never replaces a working scenario. Once the step screenshots from the verification run (idea 5) exist, the card can show them per step.
Basis
  • direct: the scenario row has no source or review column, and no provenance concept exists (src/db/scenarios.ts:168).
  • direct: docs/domain/runs.md:224: a run with a fixed scenario ends FAILED "so a green run always means nobody stepped in". The project already protects what green means. A draft state protects it from tests nobody has looked at.
  • direct: DESIGN.md forbids runtime internals such as ctx. and json_match in UI labels. The JSON tab shows exactly those, so it is a poor review surface.
  • direct: versions are already fingerprinted (src/scenario-version.ts), so a draft can be one more version row with a pointer.
  • external: QA Wolf human review of every AI test; ICAO readback, where the listener compares what was said with what was meant.
Rationale
The requested flow puts the UI at the point where the person takes over agent output. Without a draft marker, agent output looks the same as vetted scenarios and runs with one click, including against an environment that reports to production. A readback built from the steps shows what will actually run, so a wrong target or a missing check stands out next to the prompt.
Downsides
Schema change (a status, source and prompt on scenarios, or a draft version table) plus a new UI surface. The fresh-context review rated the full proposal and diff model as heavy. A cheaper first cut is a draft flag, the stored prompt and the readback, with no diff view. Domain docs (scenarios.md, runs.md) must change in the same commit.
4

Probe the dev app by target name

Seeing the real appConfidence 70%Complexity Medium
Description
Add a probe endpoint per target, restricted to environments that allow agents. Web returns an accessibility snapshot with candidate selectors. Android returns the uiautomator tree reduced to selectors the mobile driver accepts, ranked id= first, then text=, then relative below/above, with how many elements each one matches. HTTP returns a redacted recent exchange for the endpoint. The output is already in the scenario's selector grammar, so the agent copies a selector instead of guessing it. It can also name an element ("the button labelled Sign in") and get the most stable selector for it back.
Basis
  • direct: mobile-ui.xml is written only on failure (src/drivers/mobile.ts:189-206), and the web trace is kept only on failure (src/drivers/web.ts:402). The capture code exists but runs only after something breaks.
  • direct: the mobile selector grammar is id=, text= or a bare full-match regex (src/drivers/mobile.ts:213-219), and src/drivers/adb-flow.ts already parses resource-id and content-desc and supports relative selectors.
  • external: Maestro MCP reads the live hierarchy before writing flows; the Playwright planner explores the live app first.
  • reasoned: a full-match text regex is easy for an agent to get wrong (case, punctuation, trailing space). Code that reads the dump and picks resource ids first produces the selector a careful person would pick, every time.
Rationale
A guessed selector is the most common reason an agent-written e2e step fails on its first run. This turns the agent from guessing into reading, using machinery the runner already has.
Downsides
Needs a running app or device at authoring time. Android probing inherits the device quirks the driver already works around (uiautomator hangs, Transsion keyboards). Must be blocked on production environments (see idea 5).
5

The tool checks the agent's "done"

Validate and self-correct loopConfidence 75%Complexity Low
Description
An agent finishes when the tool, not the agent, says the scenario passed cleanly: N repeats under --strict with zero recovered steps, on an environment marked agent_runs: allowed. The agent hands over the run id, and the draft card shows "Verified 3/3 strict". Agent-started runs and probes are refused on any environment without the flag, whatever E2E_ENV says. The validator also rejects raw URLs, ports and device serials in steps.
Basis
  • direct: src/run-result.ts already turns "passed only on retries" into a failure under strict, and src/runner.ts counts recovered steps; --repeat exists (src/cli.ts).
  • direct: src/config.ts:159 picks the environment from process.env.E2E_ENV, which any agent shell can set.
  • direct: domain invariant: steps name targets, never raw URLs, ports or serials (docs/domain/README.md). Project rule: the zomilabu dev app reports to production Firebase.
  • reasoned: an agent told to "run it to check" runs against whatever environment resolves, and a single green that needed a retry is a likely flake. Both guards have to live in the tool, because a line in a prompt is not enforcement.
Rationale
Flaky scenarios get caught before the person ever sees them, using the project's own definition of a clean pass. The one environment flag also makes every other agent feature (probe, verification runs, repair) safe to turn on.
Downsides
Repeat runs on Android are slow (minutes per scenario). The CLI run path for agents arrives before the UI path the user prefers, though POST /api/run could take the same options. Needs an environments.md update.
6

Repair packet with label-gated healing

Validate and self-correct loopConfidence 60%Complexity Medium-High
Description
For a failed step, one endpoint returns everything an agent needs to fix it: the step as stored, its failure label, the nearby failure-timeline entries (requests, device log lines), artifact paths, and a short list of computed candidate elements from mobile-ui.xml or the DOM that best match the missing selector. The label decides what the agent may change. On Step error it may change selectors, waits and timeouts. On Assertion failed, the assertions and extractions are locked, and any patch that changes them is marked "changes what this test checks" for the person to decide. On Environment down it changes nothing. The fix comes back as a draft (idea 3). Reports offers "Ask agent to repair" only on Step error.
Basis
  • direct: src/assertions.ts:7-19 separates "Assertion failed" (the step ran, the result was wrong) from "Step error", labelling "by what happened, not by who is to blame"; the label is stored per attempt (step_runs.failure_label).
  • direct: the failure timeline "is built when asked for, from what is already stored" (docs/domain/runs.md:129); summary.json already carries failures[].label.
  • external: Playwright's healer patches locators but marks a test test.fixme when the product is broken. Here the same rule is enforced by code, not left to the agent.
  • reasoned: the usual way an AI healer goes wrong is turning a red test green by weakening its check until it matches the bug. This project already records which kind of failure happened, so the server can tell a locator fix from a loosened check.
Rationale
Turns a red row into a proposed fix without letting the agent hide a real regression. The person reviews only the patches that change what is being tested.
Downsides
Has the most moving parts of the six, and is most useful once ideas 2-4 exist. Candidate matching for web needs the DOM snapshot that is currently discarded on pass. With low real usage, few failures exist yet to tune it on.

Rejection Summary

#IdeaReason Rejected
1Base-version write guard and live scenario-change eventSound, but it only matters once an agent and a person edit the same scenario at once. Drafts (idea 3) avoid most of that. Better as a follow-up.
2Watched scenario folder as the agent's front doorConflicts with SQLite as the source of truth: a watched import is an implicit "file wins" that can silently overwrite a builder draft. Strict HTTP plus a kit covers the same need.
3"Describe a test" box in the UI runs the coding agent headlessSpawning claude -p / codex exec from the server is a large security and operations surface. The most literal reading of the request, but it belongs in brainstorming once ideas 1-3 exist.
4Live authoring through the hold (step-hold mode)The hold exists only after a final-attempt failure, and a fixed scenario makes the run FAILED. Extending it changes run semantics. Idea 4 gives the agent the live screen with less risk.
5Assertions first, steps filled from a recorded passNo recording mechanism exists, so the cost is large and the basis is weak.
6Screen atlas harvested from passing runsUsage is low, so there is little to harvest, and traces are discarded on pass. Revisit when run volume grows.
7Style sheet learned from Pause on Failure fixesNeeds a history of corrections that doesn't exist yet. Revisit after idea 6.
8Per-step intent sentence written by the agentAgent-written prose can be wrong about what the step does. A readback the code builds from the steps (idea 3) is more trustworthy.
9Review only the delta against presets and step groupsUseful only at high agent volume. Below the bar for now.
10Watch-me-build combination (live hold plus selector resolving plus gated healing)Depends on rejected idea 4. Its useful parts are in survivors 4 and 6.
11Filmstrip review of the agent's verification runMerged into idea 3 as a later addition to the review card.
12The agent never writes a selector (resolve described elements)Merged into idea 4.
